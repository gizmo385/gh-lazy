# B105: Pasted links ignore the host, and `http://` links are unknown

- Id: B105
- Status: open
- Answer:
- Python reference: `ui/screens/link_paste.py` `REPO_PATTERN_STRING`, `REPO_PATTERN`, `ISSUE_PATTERN`, `PR_PATTERN`,
  `USER_PATTERN`, `resolve_github_url`
- Recommendation: Keep Python's patterns as they are (unit tests pin them, case by case). Matching any host is what
  lets a GitHub Enterprise link resolve against the configured host, and `http://` links are rare enough (browsers
  copy `https://`) that changing the rules isn't worth a difference.
- Rows: `markdown-links.github-url-patterns`

The repo, issue and pull request patterns are `(https://)?[^/]+/<owner>/<repo>` plus `/issues/<n>` or `/pull/<n>`,
matched from the start of the text but not to its end. So:

- The host isn't checked. `https://gitlab.com/parity-bot/pr-details/pull/5/files` opens GitHub's
  `parity-bot/pr-details` PR 5 with "Opening pull request for link" (Python-only probe, not committed), and so does
  `example.org/parity-bot/pr-details/pull/5`.
- `http://` doesn't fit: `[^/]+` takes `http:`, and the empty segment after it can't be an owner. Every `http://` link
  toasts "Unknown link" (probe: `http://github.com/parity-bot/pr-details`).
- Anything after the repo name that isn't `/issues/<n>` or `/pull/<n>` opens the repo:
  `https://github.com/o/r/actions/runs/1` and `https://github.com/o/r/pulls` are the repo `o/r`.
- A query or fragment right after the repo name becomes part of the name: `https://github.com/o/r?tab=readme` asks
  for `GET /repos/o/r?tab=readme`, which GitHub answers for `o/r` (it ignores the query); with `#readme` the repo
  name asked for is `r#readme`.

The user pattern is stricter: `(https://)?github\.com/<login>/?` to the end of the text, so a user link on another
host is unknown (unless it has a second segment, when it's a repo link).

Found while designing the paste link modal (#197).
