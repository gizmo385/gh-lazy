# B109: A slow preload replaces a newer selection, or loads the wrong repo's PR

- Id: B109
- Status: answered
- Answer: Follow the recommendation. ([Chris, 2026-10-30](https://github.com/gizmo385/gh-lazy/issues/198#issuecomment-6532915983))
- Python reference: `ui/widgets/pull_requests.py` `PullRequestsContainer.load_pull_request_for_current_commit`; `lib/github/pull_requests.py` `list_pull_requests_for_commit`; `ui/screens/primary.py` `SelectionsPane.load_repository`, `LazyGithubMainScreen._open_link_subject`, `MainViewPane.load_pull_request`
- Recommendation: Treat the preload as a selection that any newer one replaces, as #170's selections already do (B45's answer): selecting a repo, a PR, an issue or a run, or opening a link or a notification, cancels the commit lookup and the PR fetch it started, and drops their late answers. The lookup's PRs belong to the repo it was asked about, never to whichever repo is current when it answers.
- Rows: `pull-requests.preload-superseded`

`load_pull_request_for_current_commit` is a plain `@work` worker: nothing cancels it when something else is selected,
and its result is posted as `PullRequestSelected` whenever it arrives. So a lookup that's still running when the user
picks something else replaces that choice with the current commit's PR once it answers. Opening a link to a PR in the
current-directory repo hits this without any slowness: `_open_link_subject` calls `set_repository`, which only starts
the worker, then shows the linked PR at once; the worker's `gh api` call answers after that, and the details switch
to the current commit's PR (found by reading the code).

`list_pull_requests_for_commit` also builds the PRs with `repo=LazyGithubContext.current_repo` read after the request
returns, not the repo it asked. Reproduced under the parity harness (#198) with a 3 s delay on the
`/repos/parity-bot/pr-details/commits/<sha>/pulls` fixture: launched in a `pr-details` checkout on `new-feature`
with the setting on, then selecting `parity-bot/dotfiles` before the lookup answered. When it answered, Python logged
`Loading PR for your current commit`, asked for `GET /repos/parity-bot/dotfiles/pulls/5` (the number of
`pr-details`' PR, in the newly selected repo) and, on its 404, showed the error toast "API Error" / "Error fetching
pull request!". Had `dotfiles` a PR #5, the details would have shown that unrelated PR under the dotfiles status line.
