# B119: A large markdown body freezes the app, and a selection made meanwhile never shows

- Id: B119
- Status: open
- Answer:
- Python reference: `ui/widgets/issues.py` `IssueOverviewTabPane.compose`, `ui/widgets/pull_requests.py`
  `PrOverviewTabPane.compose`, `ui/widgets/repository_details.py` `RepoOverviewTabPane.load_readme`, each a
  Textual `Markdown`; Textual 8.2.5 `widgets/_markdown.py` `Markdown.update` (markdown-it parses in an executor,
  then the blocks are built and mounted on the event loop, 200 at a time); `ui/screens/primary.py`
  `MainViewPane.load_issue` (`clear_panes`, then `add_pane`)
- Recommendation: Don't reproduce it. The Rust app keeps drawing and taking keys while a large body is prepared,
  shows the header and rule with nothing below the rule until the body is ready (what Python shows before its
  first batch of blocks mounts), and a selection made meanwhile replaces the Overview at once; the old body's
  result is dropped (#337).
- Rows: `markdown-links.large-body`

Textual's `Markdown` turns every block of the document into a widget. For an issue whose body is about 1 MB (about
5,000 paragraphs and a 500-row table), parsing is quick, but building and mounting the widgets keeps the event
loop busy: the Overview's header and the first blocks show, and then the screen doesn't change for about 30
seconds. Keys typed meanwhile are queued: `tab` then `end` pressed just after the first blocks show do nothing
visible until every block is mounted, then scroll to the end.

Selecting another issue while the body is still mounting is worse. With issue #12's 1 MB body showing its first
blocks, `3 j enter` (focus Issues, move to #11, select it) left the screen on #12's Overview; 3.5 minutes later
it still showed #12, and #11's Overview never appeared.

Seen with the parity harness on a copy of the `issue-details` fixture set whose issue #12 has a 1 MB body
(`perf_tests.rs`'s `large_markdown(1 << 20, 500)`), at 160x48.

Found while designing #337.
