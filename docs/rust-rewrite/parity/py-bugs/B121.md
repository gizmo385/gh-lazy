# B121: Keys typed right after tab or shift+tab can reach the widget that had focus

- Id: B121
- Status: answered
- Answer: Follow the recommendation: keep Rust's order, the same answer as B98. (Chris, 2026-10-31, [comment](https://github.com/gizmo385/gh-lazy/issues/353#issuecomment-6540155780))
- Python reference: Textual 8.2.5 `app.py` `App.on_event` (forwards each key to `self.focused` when it reads it),
  `App._on_key` and `App._check_bindings` (run the `tab`/`shift+tab` binding only once that key has bubbled up from
  the old widget), `screen.py` `Screen._move_focus`, `Screen.set_focus`
- Recommendation: As for B98: keep the Rust behavior, where keys apply in the order they're typed, so `tab` then
  typing always types into the next field. Don't reproduce the race. Parity scenarios wait for focus to land after
  `tab`/`shift+tab` (#360).
- Rows: `main-layout.focus-ring`, `modals.dialog-focus-order`

When the app is busy, each key goes to the widget focused when Python reads it, and the focus only moves when the
`tab` reaches the app's binding. In the New issue modal, `tab` then `First line` typed quickly from the title field
types `First line` onto the end of the title (the issue is created as `Parity titleFirst line`), and
`tab tab tab enter` from the modal's scroll area can type a newline into the description instead of pressing Save.
Seen in `issue-new` under CPU load (6 of 6 Python runs, 2026-10-31) and in `settings-keys` (4 of 6). Typed slowly,
the same keys do what the focus ring says.

Found while designing #353 and #360.
