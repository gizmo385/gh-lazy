# B180: The PR table lists PRs out of the issues endpoint, so recent issues can hide every PR

- Id: B180
- Status: answered
- Answer: Fix it: list PRs from their own endpoint (Chris, 2026-10-31, in #384's body: "owner preference: the
  proper one"). See [pr-list-from-pulls-endpoint](../decisions/pr-list-from-pulls-endpoint.md).
- Python reference: `lib/github/issues.py` `list_issues`; `ui/screens/primary.py`
  `SelectionsPane.fetch_issues_and_pull_requests`; `lib/messages.py` `IssuesAndPullRequestsFetched.pull_requests`;
  `ui/widgets/pull_requests.py` `fetch_more_pull_requests`, `on_issues_and_pull_requests_fetched`
- Recommendation: Page the PR table through `GET /repos/{owner}/{repo}/pulls` (`owner_filter = all`) or
  `GET /search/issues?q=is:pr repo:… author:@me` (`owner_filter = mine`), so every page is all PRs.
- Rows: `pull-requests.rows-from-issues`, `pull-requests.filters`

Both PR pages and issue pages come from `GET /repos/{owner}/{repo}/issues`, 30 items, newest first, and the PR table
keeps the items with a `draft` key. When the newest 30 items are all issues the PR table gets no rows, collapses to
`[2] Pull Requests (empty)`, and with no row to put a cursor on it never asks for page 2. So it stays empty however many
PRs the repo has. On 2026-11-01 `gizmo385/gh-lazy`'s page 1 (#392 to #363) and page 4 hold no PRs, though it has 71.
With `owner_filter = mine` the same happens to anyone whose newest 30 issues and PRs in a repo are all issues.

B44's answer keeps paging going past a page with no PRs once the table has a row; it can't help a table that never
gets one. Reproduced with the `pr-list-issues-first` fixture set (#384): Python shows the Issues table's 30 issues
and `[2] Pull Requests (empty)`, and its only page-2 request is the Issues table's.

Found by Chris testing locally on 2026-10-31 (#384).
