# B181: An Issues table whose loaded pages hold no issues stays empty

- Id: B181
- Status: open
- Answer:
- Python reference: `lib/github/issues.py` `list_issues`; `ui/widgets/issues.py` `fetch_more_issues`,
  `on_issues_and_pull_requests_fetched`; `ui/widgets/common.py` `LazilyLoadedDataTable.load_more_data`
- Recommendation: Keep `GET /repos/{owner}/{repo}/issues`, and while the Issues table has no rows after a page that
  wasn't empty, ask for the next page without waiting for a cursor move, up to 5 pages in all, and not at all for a
  repo with issues turned off (`has_issues: false`). See #399 for the options.
- Rows: `issues.filters`

The Issues table pages through the same mixed endpoint as the PR table did before #384 (B180), dropping the PRs. When
the newest 30 items are all PRs (repos where bots open PRs, or `owner_filter = mine` for someone who mostly opens
PRs), the table gets no rows, shows `[3] Issues (empty)` and never asks for page 2. B44 left this case as it is and
named fetching ahead as an option for Chris. There's no REST endpoint that lists only issues; `GET /search/issues`
with `is:issue` does, but under a 30-requests-a-minute limit, a 1,000-result cap and a search index that lags behind
new issues.

A repo with issues turned off still lists its PRs on the issues endpoint (`git/git` on 2026-11-01: `has_issues:
false`, page 1 is 30 PRs), so fetching ahead without the `has_issues` check would page through every PR of such a
repo.

Found while speccing #384.
