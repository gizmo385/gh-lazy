# B33: The GITHUB_CLI backend loads only the first page of repositories

- Id: B33
- Status: open
- Python reference: `lib/github/repositories.py` `_list_for_page`, `lib/github/backends/cli.py` `parse_cli_api_response`
- Recommendation: Rust pages through every `rel="next"`, as Python's default `RAW_HTTP` backend does. Fix #134, or accept the difference in `table-navigation` (`bottom`) until it's fixed.
- Rows: `repositories.rows`

`_list_for_page` reads the pagination header as `response.headers.get("link")`. The `GITHUB_CLI` backend stores headers in
a plain `dict` under the name `gh api -i` prints, which is Go-canonical `Link`. The lookup misses, so `_list` stops after
page 1 and an account with more than 50 repositories sees only 50. The default `RAW_HTTP` backend uses httpx's
case-insensitive headers and pages correctly, so few real users hit this. The parity harness runs Python with
`GITHUB_CLI`, though.

Found while implementing #100 ([PR #135](https://github.com/gizmo385/gh-lazy/pull/135)): with the `repos-60` fixture,
the `table-navigation` scenario's fake-gh log has a single `page=1` request, and Python's `bottom` capture ends at the
50th repo. Filed as #134. Until Chris answers, the recommendation stands.
