# B43: A failed or malformed list page crashes the app

- Id: B43
- Status: answered
- Answer: Follow the recommendation. (Chris, 2026-10-26, in a Claude Code session; see #171)
- Python reference: `ui/widgets/common.py` `LazilyLoadedDataTable.load_more_data`; `ui/widgets/pull_requests.py` `fetch_more_pull_requests`; `ui/widgets/issues.py` `fetch_more_issues`; `lib/github/workflows.py` `list_workflows`, `list_workflow_runs`; `ui/widgets/workflows.py` `WorkflowsContainer.load_repo`
- Recommendation: Don't crash. A failed PR or issue page logs `API Error fetching issues and PRs from Github API` at ERROR, keeps the rows and the paging state, and the next cursor move asks for the page again (#102's hook already retries). A workflows or runs response that doesn't decode is handled like an HTTP error: Python's ERROR line, and an empty list.
- Rows: `searchable-tables.lazy-loading`, `pull-requests.filters`, `issues.filters`, `workflows.loading`

`load_more_data` runs in a `@work` worker and catches nothing. When the PR or issue fetcher's `list_issues` raises
`GithubApiRequestFailed` (any HTTP error on page 2 or later), the worker fails, and Textual's default
`exit_on_error` exits the app with a traceback. A Python-only probe with `prs-70` and a 500 on page 2 of
`parity-bot/lazy-fixture`'s issues exits at the `G` that asks for it. Only the shared first page
(`fetch_issues_and_pull_requests`) is guarded.

The workflows fetchers catch only `GithubApiRequestFailed`. A body pydantic rejects (a missing required field, an
unknown `WorkflowState`) raises out of the `WorkflowsContainer.load_repo` worker in the same way.

Found while speccing #171, #172 and #173. Until Chris answers, the recommendation stands and the specs follow it.
