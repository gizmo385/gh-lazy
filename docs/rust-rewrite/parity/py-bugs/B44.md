# B44: PR and issue paging stops at a page with none of the table's kind

- Id: B44
- Status: answered
- Answer: Follow the recommendation. (Chris, 2026-10-26, in a Claude Code session; see #171)
- Python reference: `ui/widgets/common.py` `LazilyLoadedDataTable.load_more_data`; `ui/widgets/pull_requests.py` `fetch_more_pull_requests`; `ui/widgets/issues.py` `fetch_more_issues`
- Recommendation: End paging only when the API page itself is empty. A page that adds no rows of the table's kind keeps paging on, and the next cursor move asks for the page after it. Rust doesn't fetch further pages without a cursor move, so the requests match Python's wherever every page has both kinds.
- Rows: `pull-requests.rows-from-issues`, `issues.filters`, `searchable-tables.lazy-loading`

PRs and issues share the issues endpoint, and each table filters a page down to its own kind before handing it to
`load_more_data`, which sets `can_load_more = False` when the filtered list is empty. In a repo where one page of 30 holds
only issues, the PR table stops there for good, though older pages hold more PRs, and the other way round.

A related case is left as it is: a table whose shared first page has none of its kind is empty and ` (empty)`, has no
rows to move a cursor over, and so never pages, in either app. Fetching ahead until a row lands would fix it, at the
cost of requests Python doesn't make. That's an option for Chris, not the recommendation.

Found while speccing #171 and #172. Until Chris answers, the recommendation stands and the specs follow it.
