# B45: A slow fetch for the previous repo lands in the new repo's tables

- Id: B45
- Status: open
- Python reference: `ui/screens/primary.py` `SelectionsPane.fetch_issues_and_pull_requests`; `ui/widgets/pull_requests.py` and `ui/widgets/issues.py` `on_issues_and_pull_requests_fetched`; `ui/widgets/workflows.py` `WorkflowsContainer.load_repo`, `WorkflowRunsContainer.load_repo`
- Recommendation: Drop the answers for a repo that's no longer selected, and cancel its requests when a new one is selected (#170's `load_repo` contract).
- Rows: `pull-requests.loading`, `issues.loading`, `workflows.loading`

The fetch workers aren't exclusive and nothing cancels them on a new selection. `IssuesAndPullRequestsFetched` carries
the repo, but the handlers don't compare it with the current one, and the runs worker adds its runs unconditionally.
So when repo A's first page arrives after repo B was selected and its tables were cleared, A's PRs, issues or runs are
added to B's tables, and the load function and paging state are reset as if B's page had arrived. B's own page then
adds to the mix. It needs a slow network to show.

Found while speccing #171, #172 and #173. #170 already treats it as a race not to copy. Until Chris answers, the
recommendation stands and the specs follow it.
