# B51: Lookup modals ignore keys while a lookup is in flight, then apply them to the next screen

- Id: B51
- Status: open
- Python reference: `ui/screens/lookup_repository.py` `LookupRepositoryModal.action_submit`;
  `ui/screens/lookup_issue.py` and `ui/screens/lookup_pull_request.py` `action_submit`; Textual `MessagePump`
  (one message at a time per screen)
- Recommendation: Keep the dialog responsive while the lookup runs. `modal.close` (and Cancel) closes it at once,
  cancels the request (`Effect::Cancel`) and drops a late answer, so nothing is selected. A second submit while one
  is in flight is ignored. Typing and focus moves work as usual.
- Rows: `modals.lookup-in-flight`

The Lookup button's `Button.Pressed` handler (`action_submit`) awaits the GitHub request inside the screen's
message handler. Textual handles a screen's messages one at a time, so while the request is out every key that
reaches the modal (escape, `q` outside the input, tab, typing) waits in its queue. When the answer comes back the
handler either dismisses the modal with the result or toasts an error; only then do the queued keys run, and after a
dismiss they run against whatever is on top, normally the main screen.

So a user who presses escape because the lookup is slow can't cancel it: the modal stays up until GitHub answers,
then closes with the repo, which is added to the table and selected anyway, and the escape lands on the main screen.
A Python-only probe with a lookup answered after 2 s (`O`, type a name, tab, tab, enter, escape; not committed)
showed the modal open until the answer, then the repo added and selected, with its issues, workflows, runs and
README requested.

The issue and PR lookups have the same handler shape, so the same applies to them.

Found while designing the Lookup repository modal.
