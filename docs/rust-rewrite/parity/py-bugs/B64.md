# B64: Issue comments and a run's jobs stop at GitHub's first page of 30

- Id: B64
- Status: answered
- Answer: Follow the recommendation. (Chris, 2026-10-26, in a Claude Code session; see #239 and #240)
- Python reference: `lib/github/issues.py` `get_comments`; `lib/github/workflows.py` `get_workflow_jobs`
- Recommendation: Fetch every page (`gh api --paginate`, with `--slurp` for the jobs' object pages), so an issue shows all its comments and a run all its jobs. The first request is the same as Python's.
- Rows: `issues.comments-tab`, `workflows.jobs-tab`, `workflows.overview-jobs-summary`, `workflows.logs-tab`

`get_comments` requests the issue's `comments_url` and `get_workflow_jobs` requests
`/repos/<owner>/<repo>/actions/runs/<id>/jobs`, each once, with no `page` or `per_page`. GitHub answers both with its
default page of 30 items and a `Link: rel="next"` header that nothing follows. So an issue with 45 comments shows
the first 30 (the oldest) and nothing says more exist, and a run with a 40-job matrix shows 30 jobs in the Overview,
the Jobs tab and the Logs tab. Long discussions and matrix builds are common.

The PR Conversation tab calls the same `get_comments` for a pull request's comments, so it's affected too; its rows
are the PR details design's.

Found while designing the issue Comments tab and the run details. Until Chris answers, the recommendation stands and
the specs follow it.
