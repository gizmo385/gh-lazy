# B79: Branch lists stop at GitHub's first page of 30

- Id: B79
- Status: open
- Python reference: `lib/github/branches.py` `list_branches`; its callers `ui/screens/trigger_workflow.py` `TriggerWorkflowContainer.fetch_branches` and `ui/screens/create_or_edit_pull_request.py` (the Base and Compare inputs' suggestions)
- Recommendation: Fetch every page (`gh api --paginate`), as B64's answer does for comments and jobs, so the Trigger workflow and Create PR inputs suggest every branch. The first request stays Python's `page=1&per_page=30`, so the fixtures and the request logs don't change for a repo with fewer than 30 branches.
- Rows: `modals.trigger-workflow`, `modals.create-pr-branches`

`list_branches` asks for `GET /repos/<owner>/<repo>/branches?page=1&per_page=30` once and never follows GitHub's
`Link: rel="next"` header. In a repo with more than 30 branches, every branch past the first 30 (GitHub lists them
in name order) is never offered as an inline suggestion: in Trigger workflow's Branch input, or in Create PR's Base
and Compare inputs. The branch can still be typed in full, so nothing is blocked, but a user who relies on the
completion can't tell the branch exists.

The Rust app follows Python until this is answered: `Github::list_branches` (#264) and `Github::list_branches_uncached`
(#277) both stop at the first page.
