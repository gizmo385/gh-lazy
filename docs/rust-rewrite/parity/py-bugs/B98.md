# B98: Keys typed right after a focus key go to the section that had focus

- Id: B98
- Status: answered
- Answer: Follow the recommendation. (Chris, 2026-10-29, [comment](https://github.com/gizmo385/gh-lazy/issues/294#issuecomment-6511007074))
- Python reference: `ui/screens/primary.py` `MainViewPane.action_focus_section`, `action_focus_workflow_tabs`,
  `action_focus_tabs` (each calls `Widget.focus()`); Textual 8.2.5 `widget.py` `Widget.focus` (defers the focus
  change with `self.app.call_later(set_focus, self)`)
- Recommendation: Keep the Rust behavior: keys apply in the order they're typed, so `3` then `j` always moves the
  Issues cursor. Don't reproduce the race. Parity scenarios that send a focus key wait for the focused section's
  footer before sending the keys meant for it (#294).
- Rows: `main-layout.focus-switching`

`1` to `6` don't move focus when the key is handled: Textual's `Widget.focus()` queues the change on the app's
message queue with `call_later`. Keys that already sit in that queue behind the focus key are dispatched first, to
the widget that still has focus. When the app is busy (a slow machine, or a big table being drawn), typing `3 j j u`
quickly from the Pull Requests table moves the PR cursor down two rows and opens the PR author's profile, then
focuses Issues; typed slowly, the same keys move the Issues cursor and open the third issue's author.

Seen in the `user-profile-authors` scenario under CPU load (#294): 12 of 12 Python runs moved the PR cursor to #93,
focused Issues with its cursor still on #100, and opened Parity Bot's profile instead of Parity Friend's. The same
keys pass when the scenario waits for ` O Lookup Issue` in the footer after `3`.

Found while designing #294.
